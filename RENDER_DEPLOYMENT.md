# Deploy De-Greenacres to Render

This repository is configured to run as a **Render Node.js web service**. It is not a static export: the application uses Next.js server rendering, route handlers, authentication cookies, image optimization, and `proxy.ts`.

## Included configuration

- `render.yaml` — Render Blueprint for the `main` branch in Frankfurt
- `.nvmrc` — Node.js 22.23.4
- `npm ci && npm run build` — reproducible production build
- `npm run start` — starts Next.js on Render's assigned `PORT`
- `/api/health` — dependency-free HTTP health check
- `next.config.js` — portable security, CORS, service-worker, and manifest headers
- `NEXT_SERVER_ACTIONS_ENCRYPTION_KEY` — generated by Render for stable server-action encryption

Review the instance plan shown by Render before creating the service. The Blueprint does not force a paid plan selection.

## 1. Prepare Supabase and Resend

1. Create or open the Supabase project.
2. Back up the target database. For a fresh database, run `supabase-schema.sql` first and then `supabase-production-cms-migration.sql`. For an existing database, review and apply the production migration during a controlled maintenance window; test the same sequence on staging first.
3. The production migration creates the public `property-images` bucket and its owner/admin RLS policies. Verify that bucket and policies after the migration; do not substitute a service-role key or make private document buckets public.
4. Copy the Supabase project URL and **anon/publishable key**. This application is designed for anon-key access with Row Level Security; do not add a service-role key to Render.
5. Create a Resend API key and verify the sender domain used by `EMAIL_FROM`.

## 2. Create the Render service with the Blueprint

1. Commit and push this migration to the GitHub repository's `main` branch.
2. In Render, select **New → Blueprint**.
3. Connect `leephil1907-lab/Degreensacre` and confirm the detected `render.yaml`.
4. Review the service name, region, branch, and instance plan.
5. When prompted, enter the environment values marked `sync: false`:

| Variable | Required value |
| --- | --- |
| `NEXT_PUBLIC_SUPABASE_URL` | `https://YOUR_PROJECT.supabase.co` |
| `NEXT_PUBLIC_SUPABASE_ANON_KEY` | Supabase anon/publishable key |
| `NEXT_PUBLIC_SITE_URL` | Expected Render URL, for example `https://degreensacre.onrender.com`, or the final HTTPS custom domain |
| `RESEND_API_KEY` | A newly created Resend API key |

Render supplies `PORT` and `RENDER_EXTERNAL_URL`; do not set either manually. Non-secret company, WhatsApp, and sender settings are declared in `render.yaml` and can be changed in **Environment**.

6. Create the service and wait for the build and health check to finish.

If Render assigns a different `onrender.com` hostname, update `NEXT_PUBLIC_SITE_URL` to the assigned HTTPS URL and redeploy. `NEXT_PUBLIC_*` values are embedded during the build, so changing them requires a new deploy.

## 3. Configure authentication redirects

In **Supabase → Authentication → URL Configuration**:

1. Set **Site URL** to the same origin as `NEXT_PUBLIC_SITE_URL`.
2. Add the password-recovery redirect:
   - `https://YOUR_DOMAIN/auth/reset-password`
3. Keep the local development URLs if needed:
   - `http://localhost:3000`
   - `http://localhost:3000/auth/reset-password`
4. If a custom domain replaces the Render hostname, add its URLs before switching DNS.

## 4. Bootstrap the first administrator

Client-side sign-up metadata cannot grant administrator access. Create the first administrator only after the schema and production migration are installed:

1. Register the owner's account through the deployed `/signup` page.
2. In **Supabase → Authentication → Users**, copy that user's UUID.
3. In the **Supabase SQL Editor** (a trusted database-administrator session), run the following with the copied UUID. Do not run it as a browser RPC or expose it as a public endpoint.

```sql
UPDATE public.profiles
SET is_admin = TRUE,
    is_verified = TRUE
WHERE id = 'PASTE_THE_AUTH_USER_UUID'::uuid
RETURNING id, email, account_type, is_admin, is_verified;
```

4. Confirm that exactly one row is returned with `is_admin = true`. If no row is returned, confirm that the auth user exists and that the profile-creation trigger from the migration is installed.
5. Sign out and back in, then open `/admin`. Keep the account type unchanged; authorization uses the protected `is_admin` flag.

The profile-privilege trigger intentionally permits this trusted SQL-editor update because `auth.uid()` is null there, while preventing ordinary authenticated users from elevating their own profile. Subsequent administrators can be promoted from **Admin → Users** by an existing administrator.

## 5. Verify the deployment

Replace `YOUR_DOMAIN` with the Render hostname or custom domain:

```bash
curl -i https://YOUR_DOMAIN/api/health
curl -I https://YOUR_DOMAIN/
curl -I https://YOUR_DOMAIN/sw.js
curl -I https://YOUR_DOMAIN/manifest.json
curl -i https://YOUR_DOMAIN/api/properties
```

Expected results:

- `/api/health` returns HTTP 200 and `{ "status": "ok" }`.
- Pages and API routes return security headers from `next.config.js`.
- `/sw.js` includes `Service-Worker-Allowed: /` and a revalidation cache policy.
- `/manifest.json` has the manifest content type.
- Supabase-backed endpoints return data rather than configuration errors.

Then test these browser flows:

- Home page, property search/filter/view controls, property details and sharing at 320px, 390px, tablet and desktop widths
- Map markers only for saved coordinates, plus single-result, multi-result and no-result address searches; confirm ambiguous results require manual selection
- Registration, sign-in, sign-out, password recovery and the first-admin bootstrap above
- Protected dashboard, participant-only property messaging and non-admin rejection from `/admin`
- Create/edit/publish/moderate properties, developments, agencies, agents, insights and reviews; update global settings and verify the public contact/footer values change
- Property image upload/reordering/deletion and owner-versus-admin authorization
- Property enquiry, inspection, contact and review forms, including their persisted admin inbox records
- Individual transactional email delivery through Resend and its delivery-history record
- PWA manifest/service-worker installation; confirm API, admin and private account responses are not served from the worker cache

## 6. Move a custom domain from Vercel to Render

1. In the Render service, open **Settings → Custom Domains** and add the apex and `www` domains.
2. Create the DNS records exactly as shown by Render. For `www`, this is normally a CNAME to the service's `onrender.com` hostname; use Render's displayed target rather than an old Vercel target.
3. Wait for DNS verification and Render's TLS certificate issuance.
4. Set `NEXT_PUBLIC_SITE_URL=https://YOUR_CUSTOM_DOMAIN` in Render and redeploy.
5. Update Supabase Site/redirect URLs and the Resend sender configuration if the email domain changes.
6. Test the custom domain and keep the previous Vercel deployment available for rollback until verification is complete.
7. After the cutover is stable, remove the old Vercel domain assignments or retire the Vercel project to avoid serving stale production copies.

## Local production rehearsal

Use Node.js 22 and real local environment values. Do not commit `.env.local`.

```bash
npm ci
cp .env.example .env.local
# Fill in .env.local, then:
npm run type-check
npm run build
npm run start
```

Open `http://localhost:3000/api/health` and `http://localhost:3000`.

## Optional environment settings

- `CORS_ALLOWED_ORIGIN`: defaults to `*` for public, non-credentialed cross-origin API access. Set one trusted HTTPS origin to enable credentialed CORS. Same-origin browser requests do not need CORS.
- `NEXT_PUBLIC_GA_ID`, `NEXT_PUBLIC_GTM_ID`: analytics.
- `NEXT_PUBLIC_GOOGLE_ADSENSE_ID` and ad-slot variables: optional advertising. Unconfigured units render nothing; never deploy setup placeholders as public content. These public values require a rebuild after changes.
- `GEOCODING_USER_AGENT`: recommended server-only Nominatim identifier containing the production URL and a monitored contact email. The app still sends its safe default if omitted.
- `NEXT_PUBLIC_MAPBOX_TOKEN`: unused by the core Leaflet/OpenStreetMap map flow; leave unset unless a separate Mapbox integration is added.

Public maps use OpenStreetMap tiles and Nominatim, so their availability and usage policies remain external dependencies. Preserve the visible map attribution. Address search never invents coordinates and does not auto-select among ambiguous matches.

The built-in abuse limits are process-local. They are suitable for a single Render instance, but before running multiple instances use a shared store such as Redis/Upstash for rate limits; otherwise each instance has an independent allowance.

See `.env.example` for the complete list.

## Security note

The old deployment documentation contained a committed Supabase service-role credential and admin password. Rotate both before go-live and use only newly created values in their respective dashboards. The Resend entries found in the documentation were placeholders, not live keys. Removing values from the current branch does not remove them from Git history.
